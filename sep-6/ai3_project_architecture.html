17-Step Analysis Pipeline

Two coordinated orchestrators execute in sequence or parallel. Click any step to see implementation details.

1

Technology Determination

Input: Repository family directory → Output: modules.csv
File Scan Foundation
Scans each repository in the family to detect programming languages (Java, Python, JS), build systems (Maven, Gradle, npm), frameworks (Spring, Flask, Express), and generates a 29-column modules.csv that feeds all downstream steps. Detects: has_rest_endpoints, has_maven, has_npm, technology classification.
2

Java AST Analysis

Input: modules.csv (Java repos) → Output: Java consumers/providers CSVs
AST Maven JAR
Runs java-pattern-detector-1.0.0.jar on each Java repository. Extracts: REST endpoint definitions (GET/POST/PUT/DELETE), Spring dependency injection patterns, Feign/RestTemplate client calls, controller-to-service mappings, and Spring configuration properties.
3

JavaScript AST Analysis

Input: modules.csv (JS repos) → Output: JS consumers/providers CSVs
AST Babel
Uses Babel parser to analyze JavaScript/TypeScript codebases. Extracts: Express route definitions, Axios/fetch HTTP client calls, React component API consumption, Node.js module dependencies, and package.json dependency graphs.
4

Python AST Analysis

Input: modules.csv (Python repos) → Output: Python consumers/providers CSVs
AST Built-in
Python's built-in AST module analyzes Flask/Django/FastAPI codebases. Extracts: route decorators, request handlers, HTTP client calls (requests, httpx, aiohttp), configuration readers, and database connection patterns.
5

CSV Consolidation

Input: Language-specific CSVs → Output: Unified consumer/provider tables
Merge
Merges per-language analysis results into unified consumer and provider tables. Normalizes column schemas across Java/Python/JS, deduplicates entries, and creates the consolidated baseline for cross-repository correlation.
6

Code-to-Config Correlation

Input: Consolidated CSVs + build files → Output: Configuration mappings
Config Extraction
Resolves code references to configuration values. Maps: property placeholders to actual values, environment variable references to deployment configs, JDBC/connection strings to external system identities, and Spring profiles to runtime configurations.
7

Consumer-Provider Correlation

Input: Code + config data → Output: all_consumer_correlations.csv
Core Graph Edge List
The central artifact. Matches consumers to providers across all repos. Produces all_consumer_correlations.csv with 40+ columns: correlation_id, consumer_repo, provider_repo, endpoint URLs, match_type (DIRECT, INDIRECT, EXTERNAL), configuration_type (LITERAL, PROPERTY, IMPLICIT), and extracted hostnames/domains.
8

LLM Correlation Enhancement

Input: Low-confidence correlations → Output: Enhanced CSV with scores
LLM Heavy Hours
Sends low-confidence correlations to AWS Bedrock for semantic validation. The LLM evaluates whether consumer URL patterns truly match provider endpoints, scores confidence 0.0–1.0, and provides reasoning. This is the most time-intensive step and can be skipped for initial analysis.
9

Visualization Data Generation

Input: Enhanced correlations → Output: cross_repo_data.json
Nodes & Edges Final
Transforms the correlation CSV into cross_repo_data.json — a Cytoscape.js-ready graph structure with nodes (repos, services, external systems), edges (dependencies with metadata), and detail panels for the interactive web viewer.
1

Business Determination

Input: modules.csv → Output: Business summaries per repo (LLM)
LLM
Uses LLM to analyze each repository's codebase and generate a business summary: purpose, domain classification, key capabilities, and role in the ecosystem.
2

Business Grouping

Input: Business summaries → Output: Domain groups JSON
LLMClustering
Clusters repositories into business domains (e.g., "Portfolio Management", "Client Services", "Trading Platform") using semantic similarity of business summaries.
3

External Systems Extraction

Input: Build files → Output: Raw external systems
Parsing
Parses pom.xml, package.json, requirements.txt to identify external dependencies: databases, messaging systems, third-party APIs, authentication services.
4

C4 Systems Consolidation

Input: Raw externals → Output: ≤18 C4 boxes
LLMCardinality
Reduces hundreds of external dependencies to ≤18 meaningful C4 external system boxes using LLM-driven deduplication and semantic grouping.
5

C4 Context Model (C1)

Input: Domains + C4 systems → Output: c4_context_model.json
LLMC1 Diagram
Generates the C4 Level 1 context diagram: the platform as a single system, 8 business domains inside, 3 actor personas (Investment Advisor, WM Client, Platform Admin), and ≤18 external systems.
6

C2 Data Assembly

Input: Correlations + relationships → Output: Index tables
Indexing
Builds cross-reference indexes: repo-to-external-system, domain-to-domain, and domain-to-external mappings from correlation data.
7

C2 Relationship Wiring

Input: Data indexes → Output: Enriched relationships
LLMLabels
Uses LLM to generate human-readable relationship labels for each edge: "Fetches portfolio positions via REST", "Publishes trade events to Kafka", etc.
8

C2 Container Model

Input: All C4 data → Output: c4_container_model.json
C2 DiagramFinal
Produces the C4 Level 2 container diagram: one container per business domain, repositories within each container with roles, labeled relationships between domains and external systems.

The unified orchestrator can run phases in parallel where LLM contention is avoided:

// Parallel Phase Execution Strategy Phase 1: MR Step 1 (Foundation) // Must complete first ↓ Phase 2: MR Steps 2-7 || C4 Steps 1-2 // Parallel: no LLM contention ↓ Phase 3: MR Step 8 → C4 Steps 3-8 // LLM-heavy: serial or gated ↓ Phase 4: MR Step 9 (Visualization) // Final data generation ↓ Phase 5: Server Launch // Serve results

Shared Run ID: A single timestamp-based ID (YYYYMMDD_HHMMSS_XXXXXX) is shared across all phases, ensuring all artifacts are co-located in the same output directory.

Persistent Store: From Files to Knowledge Graph

The analysis pipeline produces rich architectural data. The persistent store transforms this from disposable output into a durable, queryable knowledge base that accumulates intelligence across runs.

Today: File-Based

CSV + JSON Flat Files

  • ● Each run creates isolated output in multi_repo_ast_output/{run_id}/
  • ● Correlations stored as CSV edge lists (40+ columns)
  • ● C4 models stored as nested JSON
  • ● State checkpoints as JSON files
  • ● No cross-run queries possible
  • ● No graph traversal or path analysis
  • ● Single-user, local filesystem access

Why Neo4j Becomes the Persistent Store

The analysis output is inherently a property graph: repositories are nodes, dependencies are edges, and both carry rich metadata. Flat files force consumers to reconstruct this graph on every query. Neo4j stores the graph natively and enables instant traversal.

Q Instant Queries

"Show all consumers of Service X" — one Cypher query vs. parsing CSV files, filtering, and joining.

Δ Drift Detection

Compare graph snapshots across runs: new dependencies, removed services, changed patterns.

⇄ Impact Analysis

"If this service goes down, what's affected?" — multi-hop graph traversal in milliseconds.

𝓒 Domain Boundaries

Query cross-domain coupling: which domains are tightly coupled? Where are the clean boundaries?

↻ Continuous Updates

Pipeline writes directly to Neo4j at step completion. No separate import step needed.

↗ Scalable Access

Multiple teams query the same knowledge base concurrently via Bolt protocol — no file locking.

Neo4j Graph Schema

The proposed graph model maps directly from all_consumer_correlations.csv and C4 model JSON. Every CSV row becomes one or more graph edges.

Example Cypher Queries

// Impact Analysis: What breaks if "account-service" goes down? MATCH (affected)-[r:CALLS]->(target:Service {provider_repo: 'account-service'}) RETURN affected.repo_id AS impacted_service, r.endpoint AS endpoint_called, r.match_confidence AS confidence ORDER BY r.match_confidence DESC
// Drift Detection: New dependencies between two analysis runs MATCH (r:Repository)-[new:CALLS]->(s:Service) WHERE new.run_id = '20260329_213637' AND NOT EXISTS { MATCH (r)-[old:CALLS]->(s) WHERE old.run_id = '20260329_103234' } RETURN r.repo_id AS consumer, s.service_id AS new_dependency, new.endpoint AS endpoint
// Domain Coupling: Which domains are most tightly coupled? MATCH (d1:Domain)-[r:INTEGRATES_WITH]->(d2:Domain) WITH d1, d2, count(r) AS num_connections, collect(r.pattern) AS patterns RETURN d1.name, d2.name, num_connections, patterns ORDER BY num_connections DESC LIMIT 10
// Data Load: Import all_consumer_correlations.csv into Neo4j LOAD CSV WITH HEADERS FROM 'file:///all_consumer_correlations.csv' AS row // Create consumer repository node MERGE (c:Repository {repo_id: row.consumer_repo}) ON CREATE SET c.technology = row.technology // Create provider service node MERGE (p:Service {service_id: row.provider_repo, endpoint: row.provider_endpoint}) // Create the relationship edge CREATE (c)-[:CALLS { correlation_id: row.correlation_id, endpoint: row.provider_endpoint, match_type: row.match_type, match_confidence: toFloat(row.match_confidence), config_type: row.configuration_type, run_id: '20260329_213637' }]->(p)

What v4.0 (Persistent Store) Enables

1 Auto-Ingest Pipeline

Each pipeline step writes directly to Neo4j. Step 7 creates CALLS edges, Step 8 updates confidence scores, C4 steps create Domain nodes.

2 Architecture Diff API

REST endpoint: GET /api/diff/{run_a}/{run_b} returns new/removed/changed dependencies between any two analysis runs.

3 Impact Assessment

Before deploying, query: "What are all downstream consumers of this service within N hops?" Powered by Neo4j APOC shortest path.

4 Architecture Governance

Define rules: "No direct domain-to-domain calls" or "All external access must go through gateway". Query violations from the graph.

5 Team Dashboard

Neo4j-backed metrics: services per domain, coupling scores, external dependency counts, dependency health over time.

6 Deprecation Tracking

Mark services as "deprecated" in Neo4j. Query: "Who still depends on deprecated-service?" Track migration progress over runs.
